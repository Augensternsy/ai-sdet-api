# 大厂级软件测试规范

## 1. 功能测试规范

### 1.1 等价类划分法

#### 1.1.1 定义
等价类划分是将输入域划分为若干个子集，每个子集中的输入数据对于发现程序中的错误是等效的。测试时从每个等价类中选取少量代表性数据进行测试。

#### 1.1.2 等价类分类
- **有效等价类**：符合需求规格说明的合理、有意义的输入数据集合
- **无效等价类**：不符合需求规格说明的、不合理的或无意义的输入数据集合

#### 1.1.3 用例设计要求
1. 为每个输入条件划分有效等价类和无效等价类
2. 设计新的测试用例，使其尽可能多地覆盖尚未被覆盖的有效等价类
3. 设计新的测试用例，使其仅覆盖一个尚未被覆盖的无效等价类
4. 重复步骤 2 和 3，直到所有等价类都被覆盖

#### 1.1.4 示例：用户注册 - 年龄字段
| 等价类类型 | 输入范围 | 测试数据 | 预期结果 |
|-----------|---------|---------|---------|
| 有效等价类 | 18-60 | 25 | 注册成功 |
| 无效等价类 | <18 | 15 | 提示"年龄必须在 18-60 之间" |
| 无效等价类 | >60 | 65 | 提示"年龄必须在 18-60 之间" |
| 无效等价类 | 非数字 | abc | 提示"请输入有效数字" |
| 无效等价类 | 空值 | (空) | 提示"年龄不能为空" |

### 1.2 边界值分析法

#### 1.2.1 定义
边界值分析法是对输入或输出范围的边界值进行测试的方法。大量错误发生在输入或输出范围的边界上，而非范围的内部。

#### 1.2.2 边界点选取原则
对于范围 [min, max]，应选取以下边界点：
- **上点**：边界上的点（min, max）
- **离点**：离边界最近的点（min-1, max+1）
- **内点**：范围内的任意点（(min+max)/2）

#### 1.2.3 用例设计要求
1. 如果输入条件规定了值的范围，则选取正好等于、刚刚大于、刚刚小于边界的值作为测试数据
2. 如果输入条件规定了值的个数，则选取最大个数、最小个数、比最大个数多 1、比最小个数少 1 的值作为测试数据
3. 如果输入/输出是有序集合，则选取第一个和最后一个元素作为测试数据

#### 1.2.4 示例：密码长度（6-20 位）
| 测试点 | 输入值 | 类型 | 预期结果 |
|-------|-------|------|---------|
| 下边界 | 6 位 | 上点 | 注册成功 |
| 下边界 -1 | 5 位 | 离点 | 提示"密码长度必须为 6-20 位" |
| 上边界 | 20 位 | 上点 | 注册成功 |
| 上边界 +1 | 21 位 | 离点 | 提示"密码长度必须为 6-20 位" |
| 范围内 | 10 位 | 内点 | 注册成功 |

## 2. Web 安全测试规范

### 2.1 XSS（跨站脚本攻击）测试

#### 2.1.1 测试场景
- **反射型 XSS**：恶意脚本通过 URL 参数注入，在响应中直接反射
- **存储型 XSS**：恶意脚本存储到服务器（如数据库），在后续页面加载时执行
- **DOM 型 XSS**：恶意脚本通过修改页面 DOM 结构执行

#### 2.1.2 测试校验点
1. 输入框注入测试：`<script>alert('xss')</script>`
2. URL 参数注入测试：`?search=<script>alert('xss')</script>`
3. HTML 属性注入测试：`" onmouseover="alert('xss')`
4. JavaScript 协议注入测试：`javascript:alert('xss')`
5. 事件处理器注入测试：`<img src=x onerror=alert('xss')>`

#### 2.1.3 预期防御结果
- 所有用户输入必须经过 HTML 实体编码处理
- 特殊字符 `< > & " '` 应被转义为 `&lt; &gt; &amp; &quot; &#39;`
- 禁止在 HTML 属性中直接拼接用户输入
- Content-Security-Policy (CSP) 头应正确配置
- 敏感操作应使用 CSRF Token 验证

### 2.2 SQL 注入测试

#### 2.2.1 测试场景
- **基于错误的 SQL 注入**：通过构造特殊输入触发数据库错误信息
- **基于布尔的盲注**：通过真假条件判断推断数据
- **基于时间的盲注**：通过延迟响应判断注入是否成功
- **联合查询注入**：通过 UNION 语句获取额外数据

#### 2.2.2 测试校验点
1. 单引号注入：`' OR '1'='1`
2. 注释符注入：`admin' --`
3. 联合查询：`' UNION SELECT username,password FROM users --`
4. 堆叠查询：`'; DROP TABLE users; --`
5. 时间盲注：`' AND SLEEP(5) --`

#### 2.2.3 预期防御结果
- 所有 SQL 查询必须使用参数化查询（Prepared Statement）
- 禁止字符串拼接构造 SQL 语句
- 数据库账户应遵循最小权限原则
- 错误信息不应暴露数据库结构
- 输入数据应进行类型验证和长度限制

### 2.3 CSRF（跨站请求伪造）测试

#### 2.3.1 测试场景
- 敏感操作（修改密码、转账、删除数据）未验证请求来源
- 表单缺少 CSRF Token 或 Token 可预测
- Token 未与用户会话绑定

#### 2.3.2 测试校验点
1. 检查所有状态修改请求是否包含 CSRF Token
2. 验证 Token 是否与当前用户会话绑定
3. 验证 Token 是否一次性使用（使用后失效）
4. 验证 Referer/Origin 头是否被正确校验
5. 检查 SameSite Cookie 属性是否设置为 Strict 或 Lax

#### 2.3.3 预期防御结果
- 所有敏感操作必须验证 CSRF Token
- Token 应使用加密安全的随机数生成器生成
- Token 有效期应合理设置（建议不超过 24 小时）
- 敏感 Cookie 应设置 SameSite=Strict 和 Secure 属性
- 关键操作应进行二次确认（如短信验证码）

### 2.4 其他安全测试项

#### 2.4.1 身份认证安全
- 密码必须加密存储（bcrypt/Argon2），禁止明文存储
- 登录失败应有次数限制（建议 5 次/15 分钟）
- 会话 Token 应设置合理的过期时间
- 敏感操作应进行多因素认证（MFA）

#### 2.4.2 数据传输安全
- 全站必须使用 HTTPS（TLS 1.2+）
- 敏感数据在传输过程中应额外加密
- 禁止在 URL 参数中传递敏感信息
- API 接口应进行签名验证

## 3. 高并发与性能压测规范

### 3.1 核心性能指标定义

#### 3.1.1 响应时间（Response Time, RT）
- **定义**：从客户端发起请求到接收到完整响应的时间
- **分级标准**：
  - 优秀：RT < 200ms
  - 良好：200ms ≤ RT < 500ms
  - 合格：500ms ≤ RT < 1000ms
  - 不合格：RT ≥ 1000ms
- **百分位要求**：
  - P50（中位数）< 200ms
  - P95 < 500ms
  - P99 < 1000ms

#### 3.1.2 吞吐量（Throughput）
- **QPS（Queries Per Second）**：每秒查询数，适用于读操作
- **TPS（Transactions Per Second）**：每秒事务数，适用于写操作
- **分级标准**（参考）：
  - 小型系统：QPS > 1,000
  - 中型系统：QPS > 10,000
  - 大型系统：QPS > 100,000

#### 3.1.3 错误率（Error Rate）
- **定义**：失败请求数占总请求数的比例
- **合格标准**：错误率 < 0.1%
- **严重告警**：错误率 > 1%
- **熔断阈值**：错误率 > 5%

#### 3.1.4 资源利用率
- **CPU 使用率**：峰值 < 80%，平均值 < 60%
- **内存使用率**：峰值 < 85%，无内存泄漏
- **磁盘 I/O**：使用率 < 70%
- **网络带宽**：使用率 < 70%

### 3.2 压测场景设计

#### 3.2.1 基准测试
- 单用户单请求，验证系统基本功能正常
- 获取单请求的基准响应时间

#### 3.2.2 负载测试
- 逐步增加并发用户数（10 → 50 → 100 → 500 → 1000）
- 观察系统性能指标变化趋势
- 确定系统的最佳工作负载点

#### 3.2.3 压力测试
- 超出系统设计容量的负载（120% ~ 200%）
- 验证系统的降级和熔断机制
- 观察系统恢复能力

#### 3.2.4 稳定性测试
- 在额定负载下持续运行（建议 24 小时以上）
- 验证系统是否存在内存泄漏、连接池耗尽等问题
- 监控资源使用趋势

### 3.3 压测工具要求
- 推荐使用 JMeter、Locust、wrk 等工具
- 压测脚本应模拟真实用户行为（思考时间、随机性）
- 压测环境应与生产环境配置一致
- 压测数据应使用脱敏的仿真数据

## 4. 异常流与容灾测试规范

### 4.1 网络异常测试

#### 4.1.1 弱网测试
- **测试场景**：
  - 2G/3G 网络（高延迟、低带宽）
  - WiFi 信号弱（丢包率 5% ~ 20%）
  - 网络抖动（延迟波动 100ms ~ 2000ms）
- **测试要求**：
  - 页面加载超时应有友好提示
  - 关键操作应支持重试机制
  - 数据提交应有防重复提交机制
  - 超时时间应合理设置（建议 30s）

#### 4.1.2 断网测试
- **测试场景**：
  - 操作过程中网络突然断开
  - 网络恢复后系统状态一致性
- **测试要求**：
  - 断网时应有明确的离线提示
  - 未提交的数据应本地缓存
  - 网络恢复后应支持断点续传
  - 状态同步应保证数据一致性

### 4.2 第三方接口异常测试

#### 4.2.1 接口超时测试
- **测试场景**：
  - 第三方支付接口超时
  - 短信服务接口超时
  - 外部数据接口超时
- **测试要求**：
  - 超时时间应合理设置（建议 5s ~ 10s）
  - 超时后应有降级方案（如切换备用接口）
  - 用户应收到明确的错误提示
  - 超时请求应记录日志便于排查

#### 4.2.2 接口返回异常测试
- **测试场景**：
  - 第三方接口返回错误码
  - 第三方接口返回数据格式异常
  - 第三方接口返回空数据
- **测试要求**：
  - 应处理所有可能的错误码
  - 数据格式异常不应导致系统崩溃
  - 空数据应有默认处理逻辑
  - 异常数据应记录日志并告警

### 4.3 数据容灾测试

#### 4.3.1 数据回滚测试
- **测试场景**：
  - 事务执行过程中发生异常
  - 批量操作部分成功部分失败
  - 数据库主从切换
- **测试要求**：
  - 事务失败时应完整回滚
  - 部分失败应有补偿机制
  - 数据一致性应得到保证
  - 回滚操作应记录审计日志

#### 4.3.2 数据备份与恢复测试
- **测试要求**：
  - 数据库应定期自动备份（建议每日全量 + 每小时增量）
  - 备份数据应异地存储
  - 恢复演练应定期进行（建议每季度一次）
  - RTO（恢复时间目标）< 30 分钟
  - RPO（恢复点目标）< 1 小时

### 4.4 服务降级与熔断测试

#### 4.4.1 降级测试
- **测试场景**：
  - 非核心功能不可用时，核心功能正常
  - 缓存失效时，系统能降级到数据库查询
  - 推荐/广告等服务不可用时，页面正常展示
- **测试要求**：
  - 降级策略应提前配置
  - 降级后应有明确的用户提示
  - 服务恢复后应自动切换回正常模式

#### 4.4.2 熔断测试
- **测试场景**：
  - 下游服务错误率超过阈值
  - 下游服务响应时间超过阈值
- **测试要求**：
  - 熔断阈值应合理设置（建议错误率 > 50% 或 RT > 5s）
  - 熔断后应有快速失败机制
  - 熔断恢复应有半开状态试探机制
  - 熔断事件应记录日志并告警

## 5. 测试文档规范

### 5.1 测试计划
- 测试范围与目标
- 测试策略与方法
- 测试资源与进度安排
- 风险评估与应对措施

### 5.2 测试用例
- 用例编号（唯一标识）
- 测试点描述
- 前置条件
- 测试步骤
- 预期结果
- 优先级（P0/P1/P2）
- 测试类型（功能/安全/性能/异常）

### 5.3 缺陷报告
- 缺陷编号
- 缺陷标题
- 严重程度（致命/严重/一般/提示）
- 优先级（P0/P1/P2/P3）
- 复现步骤
- 实际结果与预期结果
- 截图/日志附件
- 修复状态跟踪

### 5.4 测试报告
- 测试概述
- 测试执行情况统计
- 缺陷统计分析
- 风险评估
- 测试结论与建议
